# Repository Architecture: Local Coding-Agent Service

## 1. High-Level Overview

This service acts as a **single-process gateway** that:
1. Accepts OpenAI-compatible `/v1/chat/completions` streaming requests.
2. Serializes all inference requests through a **single resident GPU worker** (to avoid GPU contention and ensure deterministic resource usage).
3. Manages **prompt caching** correctly across multiple clients by isolating cache contexts per session/client.
4. Records per-request metrics (latency, token counts, cache hits/misses).
5. Handles cancellation, process failure recovery, and graceful shutdown.

### Key Design Principles
- **Single GPU Worker**: One long-lived subprocess owns the GPU. The main service communicates via IPC (Unix domain sockets or named pipes).
- **Sequential Queue**: All requests are queued and processed one-by-one to prevent GPU memory thrashing and ensure fairness.
- **Client-Isolated Prompt Caching**: Each client session gets its own cache context. The GPU worker maintains a cache per session ID, not globally.
- **Crash Resilience**: If the GPU worker crashes, the service detects it, restarts it, and fails pending requests with a retryable error.

## 2. Module Boundaries

| Module | Responsibility |
|--------|---------------|
| `api/` | HTTP server, OpenAI-compatible request parsing, streaming response formatting, authentication, rate limiting. |
| `queue/` | In-memory FIFO queue for inference requests. Enforces sequential processing. Handles backpressure. |
| `worker/` | Manages the lifecycle of the resident GPU inference subprocess. IPC communication, health checks, restart logic. |
| `cache/` | Prompt cache manager. Maps `session_id` → cache context. Ensures cache isolation between clients. |
| `metrics/` | Collects per-request metrics (latency, tokens, cache hits). Exposes `/metrics` endpoint. |
| `config/` | Configuration loading (model path, GPU device, cache size, timeouts). |
| `proto/` | Protobuf or JSON schema definitions for IPC messages between main service and GPU worker. |
| `logging/` | Structured logging with request IDs for tracing. |

## 4. Detailed Design

### 4.1 Request Flow

```
Client → API Server → Queue → Worker Manager → GPU Worker → Cache → Response Stream
```

1. **API Server** receives a `/v1/chat/completions` request.
2. Extracts `session_id` (from header `X-Session-ID` or derived from API key + conversation ID).
3. Creates an `InferenceTask` with:
   - Request payload
   - `session_id`
   - `cancel_event` (asyncio.Event)
   - `metrics` object
4. Enqueues the task into the `RequestQueue`.
5. **Worker Manager** pops the next task from the queue.
6. Sends the task to the **GPU Worker** via IPC, including the `session_id`.
7. **GPU Worker**:
   - Looks up the `CacheContext` for the `session_id`.
   - Runs inference with prompt caching enabled.
   - Streams tokens back via IPC.
   - Updates cache context after completion.
8. **API Server** streams tokens back to the client.
9. On completion, **Metrics Collector** records:
   - Total latency
   - Time in queue
   - Time in inference
   - Token counts (prompt, completion)
   - Cache hit/miss status

### 4.2 Cancellation

- **Client Disconnect**: If the client disconnects, the API server sets the `cancel_event` on the `InferenceTask`.
- **Queue Cancellation**: If the task is still in the queue, it is removed and marked as cancelled.
- **Worker Cancellation**: If the task is already being processed, the API server sends a `CANCEL` message to the GPU worker via IPC. The worker checks the cancellation flag between token generations and aborts inference.
- **Timeouts**: Each request has a configurable timeout. If exceeded, the task is cancelled.

### 4.3 Process Failure Recovery

- **Health Checks**: The `WorkerManager` periodically pings the GPU worker via IPC. If no response within a timeout, the worker is considered dead.
- **Restart Strategy**:
  1. Detect worker crash (IPC connection closed or health check failure).
  2. Mark all in-flight tasks as failed with `WorkerCrashed` error.
  3. Restart the GPU worker subprocess.
  4. Clear all cache contexts (since the worker restarted, caches are lost).
  5. Resume processing new requests from the queue.
- **Graceful Shutdown**: On SIGTERM, the API server stops accepting new requests, drains the queue, and shuts down the worker.

### 4.4 Prompt Caching Correctness

**Problem**: If two clients share the same GPU worker, their KV caches must not interfere.

**Solution**:
- Each `session_id` maps to a unique `CacheContext` in the GPU worker.
- The `CacheContext` stores:
  - KV cache tensors for the session
  - Last token position
  - Cache metadata (size, last access time)
- **Cache Isolation**: The GPU worker uses `session_id` to select the correct cache context before inference.
- **Cache Eviction**: LRU eviction per session. If total cache memory exceeds a limit, the least-recently-used session’s cache is evicted.
- **Cache Invalidation**: If a client sends a new conversation (different `session_id`), a new cache context is created. If the same `session_id` is reused, the existing cache is updated.

**Key Insight**: The cache is **not** shared across sessions. This ensures correctness but may reduce cache hit rates for identical prompts from different clients. This is a deliberate tradeoff for isolation.

## 5. Two Tradeoffs

### Tradeoff 1: Sequential Queue vs. Parallel Inference

| Aspect | Sequential Queue (Chosen) | Parallel Inference |
|--------|---------------------------|--------------------|
| **GPU Memory** | Predictable, single model load | Risk of OOM with multiple concurrent requests |
| **Latency** | Higher tail latency (queuing delay) | Lower latency for concurrent requests |
| **Complexity** | Simple, deterministic | Complex scheduling, cache contention |
| **Fairness** | FIFO ensures fairness | Priority scheduling needed |

**Why Sequential?** For a local coding-agent service, GPU memory is the bottleneck. Running multiple inferences concurrently risks OOM and cache thrashing. Sequential processing ensures stability and predictable resource usage. The tradeoff is higher latency under load, which is acceptable for a local service where throughput is less critical than reliability.

### Tradeoff 2: Per-Session Cache Isolation vs. Global Cache Sharing

| Aspect | Per-Session Isolation (Chosen) | Global Cache Sharing |
|--------|--------------------------------|----------------------|
| **Correctness** | Guaranteed isolation, no cross-contamination | Risk of cache collisions, incorrect results |
| **Cache Hit Rate** | Lower (identical prompts from different clients miss) | Higher (shared prefixes benefit all clients) |
| **Memory Usage** | Higher (multiple cache contexts) | Lower (single shared cache) |
| **Complexity** | Simple, clear ownership | Complex eviction, locking, consistency |

**Why Per-Session?** Correctness is paramount for a coding-agent service. A cache collision could lead to incorrect code generation, which is unacceptable. Per-session isolation ensures that each client’s context is independent. The tradeoff is lower cache hit rates and higher memory usage, but this is acceptable for a local service with limited concurrent clients.

---

## 6. Summary

This architecture prioritizes **correctness**, **stability**, and **simplicity** over maximum throughput. The sequential queue and per-session cache isolation ensure that the GPU worker operates predictably and that clients do not interfere with each other. Cancellation and failure recovery are handled at the worker manager level, ensuring that the service remains responsive even under adverse conditions.
